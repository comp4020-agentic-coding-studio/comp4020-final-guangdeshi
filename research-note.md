# Task-adaptive harness design for coding agents

Coding agents need an environment that helps them apply their capabilities to a development task. A harness supplies tools, context and feedback while the model works. SWE-agent shows that the interface for searching and editing code can affect software-engineering performance ([Yang et al., 2024](https://proceedings.nips.cc/paper_files/paper/2024/hash/5a7c947568c1b1328ccc5230172e1e7c-Abstract-Conference.html)). This supports treating harness design as a practical design decision. I argue that support should address identifiable task needs, with task completion and satisfaction of developer requirements as the primary outcomes. Rework and execution cost help determine whether that support is worth retaining.

Relevant information can help an agent choose more useful actions without prescribing every step. AutoCodeRover uses abstract syntax tree-aware searches over classes, methods and code snippets to gather repository context iteratively. When tests are available, spectrum-based fault localization supplies additional clues about suspicious methods ([Zhang et al., 2024](https://arxiv.org/html/2404.05427v3)). These mechanisms suggest how a harness can guide investigation while allowing the model to choose what to inspect next. The intended benefit is a closer connection between the agent's uncertainty and the information it receives. Finding an appropriate location still leaves the separate problem of making a correct change.

The evidence for this support must distinguish a workflow's performance from an individual component's contribution. AutoCodeRover's fault-localization setting also adds test-based validation and patch regeneration, so the reported improvement cannot be attributed to retrieval alone (Zhang et al., 2024). Establishing that contribution would require matched comparisons that hold the model, tasks, validation and retry policy fixed while varying retrieval support. Repeated runs would help assess variation between attempts. Until these contributions are separated, the results justify investigating structured support in comparable repository tasks, rather than adopting the entire workflow as a general requirement.

Support that directs an agent's attention can also impose unsuitable choices or unnecessary work. Comparisons of skill-guided runs with no-skill or alternative-skill runs identify functional failures and efficiency regressions, including excessive procedure ([Dong et al., 2026](https://arxiv.org/html/2608.11888v1)). The study analyses selected failure cases, not the overall failure rate of all skills. Its relevance here is that apparently useful guidance can conflict with the task or turn optional checks into mandatory work. Tools that expose useful information and instructions that prescribe a process should therefore be assessed separately. A relevant skill still needs to justify the behaviour it encourages. Useful flexibility should remain within explicit permissions and acceptance rules. Removing a redundant checklist does not justify weakening a security boundary. Similarly, allowing a model to choose its search path does not remove the obligation to verify the resulting change.

Whether support earns its place depends on the model and operating conditions. Planning, action interfaces and context management produce different effects across models, tasks and context windows ([Fan et al., 2026](https://arxiv.org/html/2609.20804v1)). Planning can support weaker-model success or reduce stronger-model cost; context management is particularly useful when the window constrains execution. A bash-capable model may need less predefined tooling, while another model may depend on that interface to execute intended operations reliably. However, planning and interface ablations are limited to T4 context management at 128k, and the interface comparison also changes validation support. These results do not isolate tool count or establish a universally preferable configuration. Task adaptation should identify a concrete difficulty, such as missing information or poor tool use, and test support against that difficulty. Context capacity must also be distinguished from total token expenditure.

The evaluation must account for the requirements and feedback available during development. FeatureLoop follows evolving requirements, checks cumulative behaviour and records corrective messages and agent token use ([Feng et al., 2026](https://arxiv.org/html/2610.35488v2)). This provides a useful precedent for separating final completion from the interaction needed to reach it. A missed established requirement calls for correction; a genuinely new requirement changes what success means from that point onward. The benchmark's fixed, simulated feedback policy cannot capture every developer judgement, and executable checks cover specified behaviours. Requirement Satisfaction should therefore include an agreed account of obligations needing human assessment.

I propose comparing harness configurations with the same model, comparable tasks, fixed initial requirements and consistent resource limits. Task Success Rate would record completed tasks under agreed acceptance conditions. Requirement Satisfaction would record individual obligations and preservation of relevant existing behaviour, making partial completion visible. First-pass Success would assess the first delivered solution against requirements already available, before corrective human feedback; internal testing and revision would remain allowed. Human–Agent Rework Cycles would count correction, revision and rechecking of missed requirements. Clarification and legitimate requirement changes would be recorded separately, so asking a necessary question would not automatically count against an agent.

Cost should cover the whole interaction, including failed attempts, corrective rounds, auxiliary model calls and execution time. Token Cost should distinguish input, output and cached usage; human review effort should be recorded separately. Fewer messages need not mean less effort, just as a cheaper run may leave more work unfinished. A harness should be retained when its contribution to accepted outcomes justifies its execution and maintenance costs. This is the proposed evaluation position, informed by the literature rather than a demonstrated improvement across all five measures. This note reports no such comparison for the Buy or Pass project.
